## VS Code MinGW 编译调试环境修复（.vscode 四个 JSON）

重写 `.vscode/` 下 tasks.json / launch.json / settings.json / c_cpp_properties.json，
目标：Ctrl+Shift+B 编译、F5 调试，MinGW 位于 `D:\mingw64\bin` 且**不写入系统环境变量**。

### 核心设计：PATH 三处局部注入（不污染全局）
- `tasks.json` → 全局 `options.env.PATH = "D:\\mingw64\\bin;${env:PATH}"`
- `launch.json` → 每个配置 `environment[].PATH` 同上（保证被调试进程加载正确的 libgcc dll）
- `settings.json` → `cmake.environment.PATH` + `terminal.integrated.env.windows.PATH`

### tasks.json 关键点
- 全局 `options.shell.executable = "cmd.exe"`，args `["/d","/c"]` — 屏蔽 PowerShell/bash 差异
- 「Configure if needed」守卫任务（`hide: true`）：
  `if not exist out\build\mingw\CMakeCache.txt cmake --preset mingw -DCMAKE_EXPORT_COMPILE_COMMANDS=ON`
  → Build 任务 `dependsOn` 它。原因：本项目 57 个 target，generate 阶段固定要 ~22-26s，
  不能每次编译都 configure。cmd 的 `if not exist` 条件不成立时 exit=0（已实测）。
- 并行：`--parallel %NUMBER_OF_PROCESSORS%`（cmd 展开）。全量重编约 71s
- 任务清单：Configure / Build(默认,Ctrl+Shift+B) / Rebuild / Clean / CTest(默认测试任务) /
  Run main.exe / Check 工具链定位(`where cmake ctest gcc g++ gdb mingw32-make`)
- problemMatcher 用 `{ "base": "$gcc", "fileLocation": ["autoDetect","${workspaceFolder}"] }`

### launch.json 关键点
- 首个配置 = `Debug (MinGW) - main.exe`（F5 默认），`preLaunchTask: "CMake: Build (MinGW)"`
  ← 标签必须与 tasks.json 完全一致，原文件用的是小写 `(mingw)`，是修复前的主要坑
- `miDebuggerPath: D:/mingw64/bin/gdb.exe`，`console: integratedTerminal`
- cwd 统一 `${workspaceFolder}`（不是 build 目录），便于测试写相对路径产物
- 新增 `Debug (MinGW) - 指定测试 exe`：`${input:mingwTestExe}` promptString，
  默认 `test_motion_control.exe`（项目有 57 个 exe，pickString 不实用）
- 保留 `CMake Launch Target` 配置（依赖 CMake Tools 扩展）

### c_cpp_properties.json 关键点
- IntelliSense 三层兜底：`configurationProvider: ms-vscode.cmake-tools`
  > `compileCommands: out/build/mingw/compile_commands.json` > `includePath`
- 删除手写的 `MINGW` / `_DEBUG` 宏（项目源码根本没用），改由 compilerPath 查询 gcc 真实内置宏
- includePath 补齐 `src` 与 `tests`

### settings.json 关键点
- `cmake.configureOnEdit: false`（避免改 CMakeLists 触发 26s 重新 generate）
- `cmake.parallelJobs: 0`（=CPU 核数）
- `cmake.debugConfig` 让状态栏小虫子调试也走 MinGW gdb
- `files.exclude` / `search.exclude` / `files.watcherExclude` 排除 `out/`

### 实测结论（本机 gcc 12.2.0 win32-seh / gdb 11.2 / cmake 4.3.1）

## 后续：CMakePresets.json PATH 隐患修复（同日）

### 隐患已用对照实验证实（不是理论推测）
在 `out/_pathprobe` 建最小工程，`add_custom_target(probe ALL COMMAND git --version)`，
两个 preset 只差 PATH 写法：
- A) `"PATH": "D:/mingw64/bin/"`（整体替换）→ **构建失败**
  `process_begin: CreateProcess(NULL, git --version, ...) failed. make (e=2): 系统找不到指定的文件`
- B) `"PATH": "D:/mingw64/bin;$penv{PATH}"`（追加）→ 成功输出 git version

**关键坑**：preset 的 `environment` 只在 `cmake --preset`（configure）和
`cmake --build --preset` 时生效；用 `cmake --build <dir>` 直接指目录**不会**应用，
第一次实验因此假阴性。必须配 `buildPresets` 才能复现。

追加后 `where gcc ld ar` 仍全部命中 `D:\mingw64\bin`，优先级不受影响。

### 实际改动（CMakePresets.json）
- 三个 preset 的 PATH 全部改为追加语义：
  mingw → `"D:/mingw64/bin;$penv{PATH}"`；unixgcc / coverage → `"/usr/bin:$penv{PATH}"`
  （unixgcc/coverage 无 Linux 环境未实测，但语义上只扩大搜索范围，
   且 toolchain 用绝对路径锁定编译器，风险极低）
- 三个 preset 均加 `CMAKE_EXPORT_COMPILE_COMMANDS`，mingw 另加 `CMAKE_MAKE_PROGRAM`
- cacheVariables 用**带类型对象**写法 `{"type":"BOOL","value":"ON"}`；
  写成裸字符串 `"ON"` 也能工作，但 CMakeCache 里类型会是 `UNINITIALIZED`
- 相应从 tasks.json 两处移除 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`，改由 preset 统一管

### 最终验证（构建树全删后冷启动）
- configure 13.0s + generate 1.4s，exit=0
- `add_executable` 56 个 → 实际生成 56 个 .exe，完全对齐
  （第 56 个是 benchmark_performance，CMakeLists 注释说明故意不注册 add_test）
- `add_test` 55 个 → **ctest 55/55 全部通过**（10.23s）
- CMakeCache 类型正确：`CMAKE_EXPORT_COMPILE_COMMANDS:BOOL=ON`、
  `CMAKE_MAKE_PROGRAM:FILEPATH=D:/mingw64/bin/mingw32-make.exe`
- gdb 断点命中 tests/main.c:53，`ptype controller` 结构体字段完整可读

### 注意
- 之前记的「57 个 exe」是旧构建树残留导致的误计，准确值是 56
- `HYD_MotionControlFB` 结构体**没有** `EN` 成员（IEC 的 EN/ENO 由 PLC 层处理），
  调试时不要 print controller.EN

## 再修：Ctrl+Shift+B 报 "No instance is currently running"（同日第三轮）

### 排查过程
- 用户无 keybindings.json，Ctrl+Shift+B 是默认 `workbench.action.tasks.build`
- 装有 `ms-vscode.cmake-tools-1.23.52`、`twxs.cmake`、cpptools 全家桶
- 该字符串在 **VS Code 本体 resources\app\out 与 CMake Tools 扩展目录里都 grep 不到**，
  WebSearch 也无标准来源 → 放弃追出处，转为「消除所有脆弱点」

### 上一版 tasks.json 的三个真实脆弱点（已全部移除）
1. `"hide": true` + `dependsOn` 依赖链 —— 隐藏任务被依赖时解析不稳
2. 任务标签前缀 `CMake: ` 与 CMake Tools 自注册的任务**争抢默认 build task**；
   若命中扩展那份且扩展未初始化完成，就会报出与构建无关的错误
3. 内联命令含 `&` `|` `(` `)`，VS Code 对 shell 任务会自动 quoting，行为不确定

### 解决方案
- **构建逻辑外移到 `scripts\build-mingw.cmd`**，tasks.json 只写 `scripts\\build-mingw.cmd`
  → 彻底规避 VS Code quoting；脚本也可在终端直接跑便于排查
  → 支持 `build-mingw.cmd [target] [rebuild]`，默认 target=all
- 删除全部 `dependsOn` 与 `hide`，8 个任务全部扁平自包含
- settings.json 加 **`"task.autoDetect": "off"`** —— 关键一招，
  禁止扩展往任务列表注入任务，Ctrl+Shift+B 只可能命中 tasks.json 里的那个
- `presentation.panel` 由 `dedicated` 改 `shared`

### ★ 重大踩坑：cmd 批处理**注释里的中文**会让脚本整体崩坏
第一版脚本我只把 `echo` 输出改成英文，注释仍用中文（以为 `@echo off` 后不显示就安全）。
结果 cmd 用 OEM 代码页(GBK)解析 UTF-8 文件，中文字节被误读，
**`rem` 行被截断、后续 `set` 行被当命令执行**，报一堆
`'埌' 不是内部或外部命令`，且 `set "PRESET=mingw"` 未生效 →
`cmake --preset` 参数为空 → `CMake Error: No preset specified for --preset`。

**铁律：Windows 上的 .cmd/.bat/.ps1 必须全文纯 ASCII（含注释）。**
校验方法：读文件字节，检查是否存在 >127 的字节。
