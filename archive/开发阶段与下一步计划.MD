# 开发阶段与下一步计划

## 1. 评审目的

结合《项目需求与设计说明书》以及当前代码实现，对该液压运动控制库在**注塑机场景**下的适用性进行审查，重点关注：

- 是否满足“工艺层 / 运动控制层解耦”的总体要求
- 是否符合 PLCopen / IEC61131-3 风格的函数块调用习惯
- 当前模块划分是否完整、清晰、可扩展
- 代码实现逻辑是否正确、是否存在嵌入式落地风险
- 下一阶段应如何组织 Sprint 与实施步骤

---

## 2. 总体结论

**结论：当前架构“方向正确，但尚未达到注塑机液压控制库的优良工程化水平”。**

从优点看，当前工程已经具备较好的雏形：

- 采用静态内存和 C99 实现，适合嵌入式平台
- 数据模型简单，具备多段配方、控制模式、结束条件等核心抽象
- 明确强调“工艺层负责机理与段切换，运动层负责数学计算与泵速输出”，总体边界是正确的
- 已具备 `MotionPlanner`、压力斜坡、诊断输出、函数块式入口等基础框架

但从注塑机液压应用的专业要求来看，当前版本仍然更接近**算法样机 / 原型库**，而不是可直接进入量产集成的控制内核。主要原因如下：

1. **模块职责尚未完全落地**：需求文档提出的 `PumpConverter`、`StateReporter`、段完成判断等模块没有真正独立，部分逻辑集中在 `motion_control.c` 中。
2. **控制模式实现不完整**：当前“位置模式”和“速度斜坡模式”在实现上几乎未区分；压力闭环仍是固定比例项，尚不足以覆盖保压、锁模等工况。
3. **状态机和函数块语义不够严谨**：`LoadRecipe()` 后即置 `ACTIVE=true`，使得库可能在未显式 `StartSegment()` 的情况下执行，和需求中“命令触发后再周期调用”的 PLCopen 风格不一致。
4. **代码中存在若干工程级风险点**：输出安全处理、诊断阈值、方向性、单位一致性、段完成逻辑复用、测试覆盖率等方面均需加强。
5. **嵌入式长期维护性不足**：类型定义、诊断模型、参数校验、配置管理、可测试性与可追踪性还需进一步规范化。

因此，建议将当前阶段定义为：

> **阶段判断：已完成基础架构验证与核心算法打样，下一步应进入“架构收敛 + 控制增强 + 质量补强”的工程化阶段。**

---

## 3. 需求符合度分析

## 3.1 与需求文档一致的部分

### 3.1.1 分层边界基本正确
需求明确要求：

- 工艺层负责液压机理逻辑、阀门控制、段切换判断
- 运动控制层只负责数学规划与泵速输出

当前实现基本遵守了这一点：

- `HDY_MotionControlFB` 负责接收当前段和反馈值
- `HDY_MotionPlanner_Execute()` 负责速度/流量/泵速计算
- 不直接控制电磁阀，也没有将机理动作写入库内

这一点是本项目最重要的架构优点，必须保留。

### 3.1.2 支持多段配方
当前数据结构 `HDY_MotionSegment` + `RECIPE[]` 已经具备：

- 多段动作描述
- 结束条件建模
- 位置 / 时间 / 压力 / 流量目标
- 段启动、段切换、段完成反馈

对合模、多段注射、多级保压的建模方向是正确的。

### 3.1.3 具备 PLCopen 风格函数块雏形
当前接口具备：

- `Init`
- `LoadRecipe`
- `StartSegment`
- `NextSegment`
- `Abort`
- `Execute`

这与“命令触发 + 周期刷新”的函数块调用模式基本一致。

### 3.1.4 具备嵌入式友好特征
当前实现优点包括：

- 无动态内存
- 固定上限 `HDY_MAX_SEGMENTS`
- 不依赖操作系统
- 代码规模小，模块边界初步形成

这些都符合嵌入式液压控制器的基本要求。

---

## 3.2 与需求存在偏差或尚未完成的部分

### 3.2.1 `PumpConverter`、`StateReporter` 尚未真正独立
需求文档中明确列出：

- `MotionPlanner`
- `MotionController`
- `PumpConverter`
- `StateReporter`

但当前代码中：

- 流量到泵速换算放在 `motion_planner.c` 内部静态函数中
- 状态与诊断上报散落在 `motion_control.c`
- 段完成判断既有独立模块，又在 `motion_control.c` 中重复实现

**结论：模块名义上存在，工程上尚未彻底分层。**

### 3.2.2 速度斜坡模式并未形成独立算法语义
需求要求支持：

- 位置控制模式
- 速度斜坡控制模式
- 压力闭环控制模式

但当前实现里：

- 非压力模式下都走同一套“位置基 / 时间基速度规划”逻辑
- `HDY_MODE_POSITION` 与 `HDY_MODE_SPEED_RAMP` 并未体现清晰差异

这意味着：**“速度斜坡模式”目前更多是枚举存在，控制策略尚未真正独立。**

### 3.2.3 压力闭环能力不足
当前压力闭环公式：

```c
commandedFlow = segment->targetFlow + 1.5 * pressureError;
```

这只是一个固定比例修正，适合作为原型，但对注塑机场景还不够：

- 保压阶段通常需要更稳定的 PI/PID 闭环
- 锁模阶段需要更明确的压力稳定区控制
- 段切换时需要避免压力指令跳变和积分突变
- 不同机构（射胶、保压、锁模）闭环参数通常不同

当前的 `RBF_PID` 虽然存在，但并未接入主执行链路，因此**需求中的压力闭环能力并未真正工程化实现**。

### 3.2.4 诊断模型不够工业化
当前诊断项有基础雏形，但仍存在问题：

- 诊断阈值直接复用 `tolerance`，未按位置 / 压力 / 流量分别建模
- 仅 `timeout` 和 `Abort` 明确写入诊断消息
- 缺少诊断代码、严重级别、发生时间、恢复条件
- 没有区分“告警”和“致命停机”

对于注塑机液压控制，这样的诊断粒度还不够支撑现场调试与售后定位。

## 4. 架构设计评估

## 4.1 当前架构的优点

### 4.1.1 总体边界是对的
工艺逻辑未侵入运动控制库，这是当前设计最值得保留的地方。对注塑机而言：

- 段切换条件、阀逻辑、低压保护、高压锁模联锁等，确实应保留在工艺层
- 运动层只做“给定 + 反馈 -> 目标流量 / 泵速”的计算，更利于复用

### 4.1.2 数据模型简洁，便于扩展
`HDY_MotionSegment` 已经具有较好的抽象基础，能覆盖：

- 合模
- 开模
- 顶针
- 抽芯
- 射胶
- 保压

后续只需要增强参数维度，不必推翻重来。

### 4.1.3 采用静态结构体承载函数块状态
`HDY_MotionControlFB` 将输入、输出、内部状态聚合在一个结构体中，这与 PLCopen 风格一致，适合：

- 多实例并行
- 周期任务调用
- 嵌入式部署

### 4.1.4 压力目标斜坡模块是正确方向
`ramp_controller` 用于缓解压力目标阶跃，符合液压系统对冲击抑制的工程需求，尤其适用于：

- 多级保压切换
- 锁模压力建立
- 压力模式段切换

---

## 4.2 当前架构的核心不足

### 4.2.1 控制器编排层过重
当前 `motion_control.c` 同时承担了：

- 命令处理
- 状态维护
- 段切换标志管理
- 诊断生成
- 段完成判断
- 调用压力斜坡与运动规划

这会导致：

- 单文件职责过重
- 未来扩展压力控制策略时容易膨胀
- 测试难以精准定位故障来源

**建议将其收敛为“编排器”角色，仅负责调度，不再承载具体策略细节。**

### 4.2.2 缺少真正的策略层
对于注塑机液压应用，至少应形成下面的策略拆分：

- 位置/速度规划策略
- 压力闭环策略
- 流量到泵速换算策略
- 段完成判定策略
- 诊断评估策略

当前这些逻辑混杂在两个源文件中，后续接入不同控制器（P / PI / PID / RBF_PID）时会变得困难。

### 4.2.3 单位和物理语义不够严谨
在 `motion_planner.c` 中，压力闭环输出流量时使用：

```c
return HDY_ClampReal(commandedFlow, 0.0, segment->maxVelocity);
```

这里 `commandedFlow` 的单位是流量，而上限使用 `maxVelocity`，这在物理量上是不一致的。说明当前模型里缺少独立的：

- 最大允许流量
- 最大泵速
- 最大压力建立斜率

这在液压系统中属于必须明确的工程参数。

### 4.2.4 方向性建模不足
当前代码默认：

- 剩余距离小于 0 则置 0
- 速度下限固定为 0
- 泵速下限固定为 0
- 位置完成条件使用 `position >= target - tolerance`

这意味着库天然偏向“单向正向运动”。

对注塑机来说，这会带来风险：

- 开模、射退、回抽等动作未必总能用同一坐标方向表达
- 如果上层使用实际机械坐标，负方向运动将无法正确规划

如果项目约定“方向由阀决定，库只给正向流量大小”，那必须在需求与接口中明确写清楚；否则当前实现方向模型是不完整的。

## 5. 模块完整性与划分合理性评估

## 5.1 模块完整性结论

**结论：模块集合“不算缺失”，但仍不完整；关键问题是“有抽象、缺实体”。**

### 已具备的模块

- 公共数据模型：`common_types.h`
- 运动规划：`motion_planner.c`
- 函数块编排：`motion_control.c`
- 压力目标斜坡：`ramp_controller.c`
- 段完成判断：`segment_completion.c`
- 预研压力控制器：`rbf_pid.c`

### 仍应补齐或独立化的模块

1. **PumpConverter 模块**
   - 从 `motion_planner` 中拆出来
   - 单独处理流量->泵速换算、限幅、方向映射、死区补偿

2. **StateReporter / Diagnostics 模块**
   - 单独生成状态、告警、故障、消息码
   - 避免在 `motion_control.c` 中直接拼装诊断

3. **RecipeValidator 模块**
   - 校验段参数是否有效
   - 检查速度、流量、压力、持续时间、容差、增益是否合理

4. **ControlStrategy 接口层**
   - 统一封装 P / PI / PID / RBF_PID 等压力控制器
   - 支持按机构或段类型切换控制算法

5. **SafetyMonitor 模块**
   - 负责 EN/Abort/Reset/超时/越界等安全停机行为

因此，从工程角度看，**当前模块设计处于“基础可运行，尚未工业化分层完成”的状态。**

## 6. 代码实现逻辑审查

## 6.1 `common_types.h`

### 正面评价
- 结构体清晰，适合静态内存管理
- 配方、反馈、诊断、状态的基础抽象方向正确

### 问题与风险
1. `HDY_REAL` 使用 `double`，对部分 Cortex-M 平台不够经济。
2. `HDY_UINT` 绑定 `size_t`，不同平台位宽不一致，不利于跨平台一致性与持久化。
3. `HDY_MotionSegment` 中缺少独立 `maxFlow`、`maxPumpSpeed`、各类诊断阈值等关键工程参数。
4. `HDY_DiagnosticInfo.message` 适合调试，不适合资源敏感型嵌入式长期使用，建议增加诊断码枚举。

### 建议
- 将 `HDY_REAL` 做成可配置类型（`float`/`double` 编译期切换）
- 对接口字段改用固定宽度整数类型
- 扩展段参数模型：速度上限、流量上限、泵速上限、压力上升率、超时阈值、允许偏差阈值分离建模

---

## 6.2 `motion_planner.c`

### 正面评价
- 位置基和时间基规划公式实现基本正确
- 非法输入保护和限幅思路正确
- 结构较小，便于替换和重构

### 主要问题
1. **压力闭环使用固定比例系数 `kP=1.5`，不可配置。**
2. **压力闭环输出流量限幅使用 `segment->maxVelocity`，物理语义错误。**
3. **非压力模式下 `targetFlow` 基本未参与控制，只通过 `velocityToFlowGain` 间接得到流量。**
4. **速度一律限制为非负值，缺少方向建模。**
5. **时间基模式仅 `a*t` 上升，没有减速区、S 曲线或终点收敛策略。**

### 结论
当前 `motion_planner` 更像一个简化版数学计算器，适合验证流程，但离液压动作的实际运动品质控制还有明显差距。

---

## 6.3 `motion_control.c`

### 正面评价
- 具备完整的 FB 生命周期入口
- 已把斜坡控制与规划调用串起来
- 支持段切换、完成信号、诊断输出

### 主要问题
1. **`LoadRecipe()` 将 `ACTIVE` 直接置为 `true`。**
   - 这会使控制器在仅加载配方后就具备执行条件
   - 不符合“命令触发后再周期执行”的 PLCopen 风格

2. **`Execute()` 在 `EN == false` 时直接返回，未强制安全输出。**
   - `PUMP_SPEED` 可能保持上一次值
   - 对液压系统存在安全隐患

3. **`Abort()` 未同步清零 `PUMP_SPEED`。**
   - 只清了 `STATE.commandedPumpSpeed`
   - 对外输出可能保持旧值

4. **最后一段完成后 `NextSegment()` 未明确清零外部输出。**
   - `PUMP_SPEED`、规划流量、规划速度可能残留

5. **段完成判断在本文件内重复实现，与 `segment_completion.c` 形成双维护点。**

6. **`STATE.currentSegmentName` 从未被赋值，状态上报不完整。**

7. **`flowDeviation` 阈值计算逻辑不合理。**
   - 复用了 `tolerance`
   - 还使用了 `min(0.1, tolerance)` 的隐含效果
   - 缺少单独的流量偏差阈值

8. **超时诊断仅覆盖 `HDY_END_TIME` 段。**
   - 实际上位置段、压力段同样需要超时保护

### 结论
`motion_control.c` 目前是整个系统中最需要优先重构的文件，应从“大而全的实现文件”收敛为“安全可控的调度层”。

---

## 6.4 `ramp_controller.c`

### 正面评价
- 实现简单、正确、可复用
- 对时间倒退做了保护
- 适合嵌入式周期调用

### 建议
- 增加输出上限 / 下限保护
- 为压力目标切换增加可选“保持、追踪、重置”策略
- 后续可支持流量斜坡、速度斜坡，形成统一的 Ramp 基础件

### 结论
这是当前代码中实现质量相对较好的模块，可保留并向通用组件演进。

---

## 6.5 `segment_completion.c`

### 正面评价
- 逻辑简洁，易懂
- 单独成模块的方向正确

### 问题
- 没有被主控制流程真正复用
- 位置完成条件仍是单方向假设
- 没有最短保持时间、稳定时间窗、连续满足周期数等工业控制常见判定方式

### 结论
该模块应该保留，但必须成为**唯一真值源**，不能继续和 `motion_control.c` 重复维护。

---

## 6.6 `rbf_pid.c`

### 正面评价
- 独立性较强
- 对未来高级压力闭环有研究价值
- 已具备初始化、更新、参数限幅等基本能力

### 问题
1. 未接入主控制链路，当前仍属“孤立模块”。
2. 命名风格与 `HDY_` 主库不统一。
3. 使用大量状态和学习参数，现场可解释性与可验证性不足。
4. 量产前缺少足够的稳定性验证、边界测试、抗噪验证和失稳保护设计。

### 结论
`RBF_PID` 应定义为**预研能力或可选策略插件**，在未完成验证前，不建议直接替代主压力控制器。

---

## 7. 嵌入式平台兼容性评估

## 7.1 适配优势

- 无堆内存分配，实时性可控
- 模块少，移植成本低
- 无复杂依赖
- 适合作为 PLC/运动控制板卡中的基础组件库

## 7.2 兼容性风险

1. `double` 在低端 MCU 上开销偏高。
2. 字符串型诊断信息占内存，且运行期价值有限。
3. 安全停机语义还不够严格，不能直接用于强实时液压控制。
4. 参数缺少统一校验和默认化机制，现场误配置风险较高。
5. 单元测试未覆盖关键故障路径，难以支撑固件版本演进。

## 7.3 结论
**从“能跑”角度看，兼容性较好；从“能稳定量产”角度看，还需要一轮面向嵌入式控制器的工程化收敛。**

---

## 8. 优先级明确的改进意见

## 8.1 P0：必须优先解决

1. **修正函数块执行语义**
   - `LoadRecipe()` 不能直接进入可执行态
   - 只有 `StartSegment()` 或 `START_SEGMENT` 命令后才能运行

2. **强化安全输出逻辑**
   - `EN=false`、`Abort()`、配方结束、非法参数时，必须立即输出安全值
   - 明确规定 `PUMP_SPEED=0`、状态非活动、规划量清零

3. **消除段完成逻辑双维护**
   - 主流程统一调用 `HDY_SegmentCompletion_Check()`

4. **拆分物理量上限**
   - 不可再用 `maxVelocity` 限制流量
   - 增加 `maxFlow`、必要时增加 `maxPumpSpeed`

5. **补上主控测试**
   - 至少新增 `motion_control` 层的单元测试与场景测试

## 8.2 P1：本阶段应完成

1. **独立 `PumpConverter` 模块**
2. **独立 `Diagnostics/StateReporter` 模块**
3. **引入可配置压力控制器接口**

## 附录：Direct / Recipe 接口语义（补充）

为便于后续集成与 HMI 展示，补充函数块在 Recipe / Direct 两种参数来源下的关键接口语义：

- **参数来源**：函数块同时保存 `RECIPE[]`（多段）与 `DIRECT_SEGMENT`（单段）两套参数，运行时由 `USE_RECIPE` 选择来源。

- **启动行为**：当 `StartSegment()` / `START_SEGMENT` 被消费并进入运行态时，FB 将把当前活动段的参数与来源锁存（latched）。这保证了运行期语义不受外部并发修改影响。

- **Direct 模式规则**：
   - `USE_RECIPE = false` 时，`StartSegment()` 忽略 `segmentIndex`，使用 `DIRECT_SEGMENT` 启动；必须先调用 `HDY_MotionControlFB_LoadDirectSegment()` 并确保 `DIRECT_SEGMENT_VALID=true`。
   - Direct 模式视为单段语义：段完成后直接进入 `DONE` / `FINISHED`，`NextSegment()` 在 Direct 模式下被拒绝并上报诊断。

- **STATE.segmentSource**：状态字段 `STATE.segmentSource`（`HDY_SEGMENT_SOURCE_NONE/RECIPE/DIRECT`）对外暴露当前或最近执行段的来源，HMI/上层可据此决定是否允许 `NextSegment()` 等操作。

- **就绪判定**：Ready/Idle 判定应基于当前选中来源：当 `USE_RECIPE=true` 时以 `RECIPE_SIZE>0` 判定为 Ready；当 `USE_RECIPE=false` 时以 `DIRECT_SEGMENT_VALID` 判定为 Ready。

以上补充与 `对话上下文-Direct与Recipe模式并存接口-已完成并通过测试.md` 保持一致，请在后续改动中优先保持“启动时锁存、Direct 完成即 DONE、Direct 下 NEXT 禁止、双模式 Ready/Idle 判定”这四条核心语义不被破坏。
