## 1. 控制链现状（实测代码路径，非文档描述）

```
工艺层：segment.mode == HYD_MODE_PRESSURE_CLOSED_LOOP
  ↓  motion_control.c:2289
ramp_controller：目标压力斜坡（pressureRampRate）
  ↓  pressureInput.{targetPressure, measuredPressure, feedforwardFlow, outputMin/Max,
  │                flowToPumpSpeedGain, pumpSpeedLimit, timestamp}      ← 注意：无 velocity / position
  ↓  pressure_controller.c:579  HYD_PressureController_Execute
  ├─ 一阶滤波 α=0.1（pressure_controller.c:6）
  ├─ 死区      （pressure_controller.c:629, HYD_ApplyPressureDeadband）
  └─ 策略分支：P / PI / PID / RBF_PI / RBF_PID
       RBF 分支 → pressure_controller.c:690 → RBF_PID_Update
  ↓
流量指令 Q* [L/min] → plannerOutput->targetFlow
  ↓
pump_converter：×flowToPumpSpeedGain → 转速 n* [rpm] → 伺服 → 泵 → 压力
```

关键事实（容易被忽略）：

- **压力控制器拿不到速度/位置**。`HYD_AxisRef` 里有 `velocity`、`position`（`common_types.h:296-297`），但 `HYD_PressureControllerInput` 没有这两个字段。→ 见缺陷 D4。
- **RBF-PID 内部不使用 dt**。整个增量计算只吃误差差分，`sampling_period` 仅用于停滞计时。→ 见缺陷 D1。
- RBF 分支输出后还叠加了三处负流量钳位（`pressure_controller.c:265 / 696` + `rbf_pid.c` 播种判据）。→ 见缺陷 D5。

## 2. 核心控制架构：被控对象到底是什么

这是必须先定的事，也是前 6 轮最薄弱的一环。

### 2.1 真实物理（立式机 / 伺服泵控 / 单泵多缸）

容腔压力方程：

```
dP/dt = (βe / V) · ( Q_pump − A·v_load − Q_leak(P, n) )
         └──┬──┘        └──┬──┘   └────┬────┘
         建压刚度      负载流量汇    泄漏（随 P、n 增大）
```

由此，**同一个"压力环"在不同工况下是三种完全不同的对象**：

| 工况 | A·v_load | 对象特性 | 控制含义 |
|---|---|---|---|
| **充液 / 运动段**（开合模、射胶前期、储料） | 大且持续 | 压力**被负载反力钳住**，流量主要变速度 | 压力环近似**开环**，反馈作用很弱；压力主要靠前馈 + 速度环 |
| **保压 / 压实段**（射胶 V-P 后） | ≈ 0 | `dP/dt = (βe/V)(Q − Q_leak(P))` → **积分 + 泄漏** | 短时是**积分器**（一点点流量就快速升压），长时由泄漏定终值。**必须抗饱和** |
| **泄压段** | ≈ 0 | 需要负流量（泵反转 / 卸荷） | 单向执行器 + 负流量限制 |

### 2.2 仿真植物与真实物理的偏差（严重）

`PressureModel_InitParams` 默认 `model_type = PRESSURE_MODEL_TYPE_FIRST_ORDER`
（`src/sim/PressureModel.c:385`），参数为 `first_order_k_bar_per_rpm = 5.4`、`τ = 1.0 s`。

实测验证（本轮新增探针 `tests/test_openloop_gain_probe`）：
2~40 rpm 全转速点 t90 **恒等于 2303 ms = 2.303τ**，确认是一阶惯性环节。

**一阶惯性 ≈ 只有"保压段带泄漏"一种工况成立，充液段（负载钳压）完全不成立。**

推论：**第 4~6 轮得到的 Mp 0.10% / ts 490 ms / σ_ss 0.077 bar 是"针对一阶模型调出来的"，不是物理上稳健的。** 真实保压段是积分器（βe/V 大、升压快得多），过冲风险显著高于仿真；真实充液段压力被负载钳住，仿真里的"升压时间"概念根本不存在。

> 这是本轮最重要的结论：**继续在一阶模型上优化参数，边际收益为零甚至为负。**

### 2.3 因此，核心架构应确定为

**"前馈定基准 + 反馈修偏差 + 抗饱和保安全"三段式，而不是"一个万能自适应 PID 打天下"。**

```
Q* = Q_ff  +  Q_fb  ──┐
     │         │      ├→ clamp(Q_min, Q_max)  →  转速
     │         └─ 增量式 PI（保压段）/ PID（可选）
     └─ Q_ff = A·v_load（负载流量汇，可算） + P_set/K（泄漏补偿，实测）
```

分段策略（工程常规做法，非过度设计）：

| 段 | 判据 | 控制 |
|---|---|---|
| 充液段 | 有速度指令 / A·v 显著 | **压力不闭环**，或仅做上限监控（防超压） |
| 保压段 | v ≈ 0，P 接近设定 | 压力闭环 PI + 抗饱和 + 前馈 P_set/K |
| 泄压段 | P > P_set 需降 | 负流量（受 outputMin 与安全钳位约束） |

## 3. 核心参数：真正需要标定的只有 6 个

当前代码里可调旋钮超过 20 个（学习率 6 个 + 增益窗口 6 个 + 滤波 2 个 + 死区 1 个 + f_velfb 3 个 + 相位阈值 3 个 + 积分钳位 3 个 + 超调驱动 4 个 + 软上限 1 个 + Jacobian 钳位 2 个……）。**现场工程师面对 20 个互相耦合的旋钮不可能调好，这本身就是缺陷。**

收敛后应只保留：

| # | 参数 | 物理意义 | 单位 | 获取方式 |
|---|---|---|---|---|
| 1 | **K** | 稳态压力/流量（泄漏特性的倒数） | bar/(L/min) | 开环阶跃实测（**已有探针**） |
| 2 | **βe/V**（或等效 τ_p） | 建压刚度 → 决定升压快慢 | bar/(L/min·s) | 开环阶跃的初始斜率 |
| 3 | **A·v_load** | 负载流量汇（运动工况最大扰动） | L/min | 结构参数 × 当前速度（**IEC 已有 velocity**） |
| 4 | **Q_max / n_max** | 泵能力上限 | L/min / rpm | 泵铭牌 × ηv |
| 5 | **ω_c** | 期望闭环带宽 | rad/s | 工艺要求（保压通常 5~20 Hz） |
| 6 | **ζ**（阻尼，0.7~1.0） | 决定超调 | — | 工艺要求 |

有了 1~6，KP/KI 是**算出来的**，不是调出来的（一阶+积分混合对象可按极点配置或 IMC 整定）。

**当前代码的增益窗口 `[0.4, 0.9] / [0.0013, 0.0056] / [0.015, 0.035]` 全是拍脑袋值**，量纲分析即可证伪：
`Td = KD·dt/KP ≈ 1e-5 s`（比采样周期小两个数量级）→ **D 项数值上等于不存在**（详见评估报告 9.2）。

## 4. 四个典型工况的实用性判定

先说一个关键前提：**立式注塑机真正需要压力闭环的只有"储料背压"和"射胶保压"两个工况**，其余以监控为主。这个前提决定了很多"不足"其实不是不足。

| 动作 | 是否用压力闭环 | 物理特征 | 判定 |
|---|---|---|---|
| **开合模** | **否**（主要用压力做监控：低压护模、锁模力确认） | 大流量、低压、负载主导，P 被机械反力钳住 | 库提供能力即可，**工艺层不应选压力闭环**。此处"压力环不好用"不是缺陷 |
| **顶针** | **否**（位置/速度动作；压力高 = 卡死，应报警而非调节） | 小流量、负载突变 | 同上，**压力监控 > 压力闭环** |
| **射胶** | **分段用**：V-P 切换前是速度控制，切换后转保压 | 高速、熔体粘度强非线性 | 真正的压力闭环只在 **V-P 后保压段**；**关键是切换无扰**，库已有 bumpless/软复位机制 ✔ |
| **储料（背压）** | **是**，最典型的压力闭环工况 | 螺杆持续后退 → 容腔体积**持续增大**，A·v 是持续大扰动 | **当前实现有明显短板** → 缺陷 D4 |

### 4.1 保压段：可用，但依赖 K

- 前馈 `P_set/K`（v6 已实现）+ 抗饱和（条件积分 + 输出限幅）都到位。
- 风险：真实保压段是**积分器**，比仿真的一阶环节激进得多，过冲风险被仿真低估。

### 4.2 储料背压：当前实现不达标

背压工况的基础流量是：

```
Q_base = A_screw · v_screw  +  Q_leak(P_set)
         └─────┬─────┘        └────┬────┘
           持续变化（随螺杆速度）   可由 K 算
```

其中 `A_screw·v_screw` 是**主导项且可精确计算**（结构参数 × 当前速度，`HYD_AxisRef.velocity` 已有）。

**现状：`feedforwardFlow = segment->targetFlow` 是一个常数**（`motion_control.c:2291`），
`HYD_PressureControllerInput` 里**根本没有 velocity 字段**。

结果：这个持续的、可预知的大扰动全部压给积分去追 → 背压建立慢、螺杆速度变化时压力大幅波动。
**这是当前压力闭环最实在的功能性短板，且不需要任何新硬件/新接口就能修。**

## 5. 缺陷清单（按严重度，均标代码位置）

### D1 【严重】采样周期未归一化，且无调用节拍保护

- `rbf_pid.c` 全篇增量计算**不含 dt**；`sampling_period` 仅用于停滞计时累加。
- `pressure_controller.c:276`：`config->dt = input->timestamp − state->previousTimestamp`，
  而 timestamp 来自 `fb->AXIS_REF.timestamp`（`motion_control.c:426`）。
- 后果：
  - 上层任务周期 1ms → 2ms，等效 `Ki = KI/dt` 减半 → **环路特性静默改变，无任何告警**；
  - 同一周期被重复调用（dt = 0）→ 积分器多走一步。
- 工程常规：增量式要么显式乘 dt，要么强制固定周期 + 断言。

### D2 【严重】RBF 自适应无可证明的稳定性边界

- `rbf_pid.c:537`：`grad_Kp = eta_p · error · sign(Jac) · |Jac| · de`
- 纯启发式梯度，**无归一化项**（无 `1/(1+|x|²)` 类因子）→ 大误差/大 Jacobian 时增益可能剧烈跳变。
- 6 个学习率 + 6 个窗口值全部未标定，且窗口本身经量纲分析已证伪（D 项失效）。
- 工程事实：**自适应 PID 在批量注塑机上的真实价值是"减少现场调参"，不是"提升动态性能"**。
  窗口没标定时，它比固定 PID 更危险。

### D3 【严重】仿真植物与真实物理不符 → 前 6 轮结论不可直接迁移

- 详见 2.2。真实保压段是积分 + 泄漏，仿真是一阶惯性。
- **这是所有"漂亮数字"的系统性偏差来源。**

### D4 【中】背压工况缺少螺杆速度前馈（功能性短板）

- 详见 4.2。`HYD_PressureControllerInput` 无 velocity；`feedforwardFlow` 为常数。
- 修复成本很低：输入结构加一个 `loadVelocity`（或直接透传 `HYD_AxisRef.velocity`），
  前馈改为 `Q_ff = loadFlowGain · v + P_set/K`。

### D5 【中】负流量（泄压）逻辑分散，三处阈值互相矛盾

| 位置 | 规则 | 阈值 |
|---|---|---|
| `pressure_controller.c:265` | 目标 & 实测 < 5 bar → 禁负流量 | 5.0 bar |
| `pressure_controller.c:696` | `|error| < 5.0` → 负流量置 0 | 5.0 bar |
| `rbf_pid.c` 播种 | `P_actual > P_set + 1.0` → 禁用前馈 | 1.0 bar |

- 三层各管一段，阈值不一致，语义无法从单一处推理 → 泄压行为难预测、难测试。
- 工程常规：泄压路径单一职责，阈值集中配置。

### D6 【中】死区双重叠加且存在边界不连续

- `pressure_controller.c:629` 用 `config.deadband` 处理一次；
- `rbf_pid.c:170` 又用 `RBF_PID_ERROR_DEADBAND = 0.005` 处理一次；
- 且 `HYD_ApplyPressureDeadband` 用的是**减法**（`error − deadband`），在死区边界引入斜率不连续
  → 易在边界产生极限环。

### D7 【中】f_velfb（压力加速度前馈）与 P 项功能重复，建议删除

- 已实证：`Σ(−kv·ΔP) = −kv·(P(k) − P(0))`，是**有界比例项**，不是微分项。
- 与 `KP·Δe` 冗余，却额外引入 4 个调参（kv 0.3/0.6/0.9 + 50% 阈值）。
- 关掉它的实测代价极小：Mp 0.10% → 0.57%，tr 371 → 332 ms。
- **建议：删掉，把 KP 按第 3 节算对即可。**

### D8 【中】软上限经 6 轮叠加，已不可推理

当前判据链：`稳态上限 → 超调驱动放宽(×40) → 2% 死区 → 峰值进展闸门(0.5bar) → 停滞闸门(0.25s) → 泄压保护(1.0bar)`。
每一层都是为修一个症状加的。**给定工况下上限是多少，现场无法预测。**

### D9 【轻】稳态判据绝对化

`rbf_pid_step_steady_state`：`|e| ≤ 5.0 bar && |du| ≤ 2.0` 持续 0.2 s。
对 100 bar 与 20 bar 工况用同一个 5 bar 阈值 → 低压段恒判"稳态"、高压段难判。应相对化（早有结论，未修）。

### D10 【轻】诊断量不足

`HYD_PressureLoopState` 已输出 adaptiveKp/Ki/Kd/Jacobian，但缺少：
**当前生效的输出上限、是否处于超调驱动窗口、停滞计时、当前前馈分量**。
现场调参只能靠猜。

## 6. 明确属于"过度设计"的部分（建议删除）

| 机制 | 判定 | 理由 |
|---|---|---|
| f_velfb 渐进非对称前馈 | **删** | 与 P 项重复，收益 <0.5% Mp，成本是 4 个调参（D7） |
| 升压段 KP×2 增益调度 | **删** | 实测 KP 窗口放大 9 倍 tr 仅变 20ms，说明升压段由限幅主导，调度无收益 |
| 相位分离积分钳位（3 档） | **收敛为 1 个** | 是"积分太强抵消 P 项制动"的补丁；积分时间按 Ti≈τ 定对后不需要 |
| 软上限的 6 层判据 | **收敛为 2 层** | 只保留"硬限幅 + 泄压保护"，抗饱和交给条件积分 |
| Jacobian 以 K 为中心限幅 | **保留** | 少数经得起推敲的改动，有物理依据 |
| 峰值进展 / 停滞闸门 | **随软上限简化一并删除** | 是为修软上限放宽后的副作用而加的 |

## 7. 建议的最小可行路径（按优先级，不做额外设计）

1. **换植物模型**（最高优先，阻塞其他一切）
   把 `PressureModel` 默认切到 `PHYSICAL_CALIBRATED`，按"容腔积分 + 泵泄漏 + 负载流量汇"标定 βe / ηv / V。
   在此之前，任何参数优化都是在拟合错误模型。
2. **现场标定 K**（已有探针与 5 步流程，见评估报告 9.6）
   把实测值写进 `segment.systemGain`——字段与接线都已就位，只是从没填过真实数据。
3. **补速度前馈**（D4）
   `HYD_PressureControllerInput` 增加 `loadFlow`（= A·v），前馈改为 `loadFlow + P_set/K`。
   这是投入产出比最高的功能性修复。
4. **收敛参数到 6 个**（第 3 节），删除第 6 节列出的冗余机制。
5. **补 dt 归一化或固定周期断言**（D1）。
6. 上述完成后，再重新跑 Mp / tr / ts / σ_ss 基线——**之前的数字作废重测**。

## 8. 修改方案与 A/B 判决（基于 Ksys 已知 + dt=1ms 固定）

### 8.1 两个确定事实带来的收敛

| 事实 | 影响 |
|---|---|
| Ksys 由工艺层传入 | K 已知 → 前馈播种/软上限/Jacobian 中心可用；KP/KI 有物理依据 |
| dt = 1ms 固定、抖动极小 | **不做 dt 归一化**（避免过度设计）；增量式参数按 dt 定值标定即可 |

### 8.2 测试台：`tests/test_pressure_ab_matrix.c`

同一植物、同一指标下逐项 A/B。指标：S1（0→150bar 阶跃）的 Mp/tr/ts，S2（100bar 保压）的 ess/σ。
**反馈链路按生产实际补齐了传感器噪声（σ=0.4 bar）+ 量化（0.25 bar）+ 前置一阶滤波（α=0.1，与 `HYD_DEFAULT_PRESSURE_FILTER_ALPHA` 一致）**——
这一点很关键：`pressure_model_step_first_order` 分支本身不施加噪声，此前所有无噪声仿真都看不见噪声相关缺陷。

### 8.3 判决结果（τ=1.0s，带噪声）

| 变体 | Mp% | tr(ms) | ts(ms) | ess(bar) | σ(bar) | 判定 |
|---|---|---|---|---|---|---|
| **V0 基线（修改前 v6）** | 0.00 | 366 | 454 | **2.556** | 0.118 | **FAIL（ess 超 1.0）** |
| **V1 删 f_velfb** | 0.56 | **330** | **380** | **-0.002** | **0.019** | **PASS** |
| V6 转 PI（删 D 项） | 0.56 | 330 | 380 | -0.002 | 0.018 | PASS |

## 9. 第 5 问：IEC 伺服泵反馈接口（转速 / 转矩 / 角度）—— 核查与补全

### 9.1 结论

**改动前：IEC 层没有泵反馈接口，属真实缺口，已补全。**

`HYD_PumpFeedback` 结构体、`HydroPump.feedback` 字段、以及仿真侧 `hydro_sim_fb.c` 的泵反馈发布**早已存在**，但这条通路**在 FB 层断开了**——没有任何入口能把泵的物理反馈写进 `HYD_MotionControlFB`，IEC 程序也读不到。原来的 13 个 IEC 功能块里，唯一与"反馈"有关的是：

| 原功能块 | 覆盖的反馈 | 缺什么 |
|---|---|---|
| `HYD_SetAxisFeedback` | 轴侧：位置 / 速度 / 流量 / 压力 | — |
| `HYD_ReadSimFeedback` | 仿真轴的位置/速度/流量/压力 | — |

### 10.2 标定原理：K 就是泄漏特性的倒数

这是本轮唯一需要"确定"的物理关系，也是第 3 节"K = 稳态压力/流量"的可计算形式。

稳定工况（负载流量 = 0）下的守恒：

```
Q_理论 = D·n/60                          [m³/s]   泵排量 × 转速
Q_泵   = Q_理论 − C_pump·P_out                    容积损失（线性泄漏）
Q_其他 = (C_out + C_cyl)·P                       管路 / 油缸泄漏
=>  D/60 = P_c · [ C_cyl + (C_pump + C_out)·(1 + C_cyl·R) ]
```

要求 `P_chamber[bar] = Ksys·n[rpm]`（Ksys = 5.0），括号内即被唯一确定，**反解出 C_out**。
改动落为闭式代码（`PressureModel.c`），而不是手写魔数——这样 D、Ksys、R 任一变化都不会
让标定悄悄失准。

**一个必须显式建模的项**：管路液阻使泵出口压力高于容腔压力，出口泄漏与泵泄漏都被放大。
我第一次手算时漏掉它，实测 **Ksys = 3.876 而非 5.0（偏差 29%）**。闭式推导已纳入。

### 10.6 本轮新暴露的问题（均为"仿真台保真度"，非控制器算法）

**P1【中】仿真台的泵流量权限比物理需要大 36 倍 → S1 升压时间被严重低估**

物理核算：0.5 L 容腔从 0 升到 150 bar，只需压缩油量

```
ΔV = V·ΔP/β = 5e-4 · 150e5 / 1.2e9 = 0.375 L
```

若要求 200 ms 内完成，需要 **1.1 L/min**。而仿真台给到 40 L/min（真实泵 20 mL/rev @ 2000 rpm），
**超 36 倍**，因此升压段必然退化为 bang-bang 并撞溢流阀。

实测（同一控制器，只改泵权限与单位换算）：

| 配置 | 最大转速 | Mp | tr | ts |
|---|---|---|---|---|
| gain=1, fmax=90（现状） | 90 rpm | 4.85% | 755 ms | 1965 ms |
| gain=50, fmax=40 L/min | 2000 rpm | 56~67% | 119 ms | 856 ms |

结论：**tr 755 ms 是仿真台的泵权限造成的，不是控制器的**；但一旦给足权限，
**超调 56~67%（= 250 bar，撞溢流阀）才是真问题**。

**P2【中】增益窗口对超调无效 → 说明限制在别处，不是增益**

扫描 Kp/Ki/Kd（默认窗口、Kp/5、Kp/10、Kp/20 及组合）：**Mp 恒为 66.67%，tr 恒为 118 ms**。
即升压段输出全程饱和在限幅上，增益不起作用。理论核对：本植物闭环
`τ_cl = V/(β·Kp)`，取 τ_cl = 40 ms 时 **Kp ≈ 0.062 L/min/bar**，而代码窗口是
`[0.4, 0.9]`——**高 7~15 倍**，印证第 3 节"增益窗口是拍脑袋值"。但要真正解决超调，
需要**接近设定值时的流量制动包络**（与位置规划器的 `sqrt(2as)` 同构），这属于新机制，
按"不过度设计"原则**本轮不引入，留待确认**。

**P3【中】管路元件（inertance/resistance/quadratic）未标定，且数值窗口很窄**

追踪显示流量几乎进不了容腔：出口压力冲到 400 bar 时容腔才 72 bar。
该元件存在**结构性两难**：
- 线性液阻大（≥1e11）→ 传输被扼流；
- 线性液阻小（≤1e9）→ 变为惯量主导，与容腔柔度构成 LC 振荡（ζ ≈ 0.003）；
- 显式欧拉稳定性又给出下界：`L ≥ β·dt²/(0.25·V) ≈ 9.6e6`，同时
  `min(V) ≥ 1.375e-4 m³`（单步升压 ≤25 MPa）。

实测 R=1e8 会使模型数值保护触发整步回退（`outlet_pressure_delta > 25 MPa`），
压力完全升不起来。**这是需要与用户确认的建模决策，本轮不擅自重参数化。**

**P4【轻】溢流阀通流能力偏小**：`relief_orifice_coeff = 1e-8` 在出口 400 bar 时只能泄
约 2.3 L/min，远小于升压段流量，因此溢流阀"钳位"实际靠压力方程而非通流平衡。

### 11.3 F1【严重】单位链不自洽：仿真台把真实泵权限隐藏了 42.5 倍

### 11.4 F2【严重·已修】植物会"冻结"：越界指令导致整步状态回退

**现象**：真实链路下压力冲到 151.58 bar 后**永久卡死**，此时控制器正在输出 −5 L/min
（全反转），电机转速还在往下掉，但出口压力 / 容腔压力 / 管路流量**全都不动了**。

**根因**：`PressureModel_InitParams` 的 `min_rpm = -100 rpm`，而控制器
`output_min_flow = -5 L/min` × gain 40 = **−200 rpm**，越界。
`PressureModel_StepInput` 入口处：

```c
if (... !PressureModel_ValidateInput(params, input)) {
    pressure_model_write_hold_output(state, out);   /* 整步不动 */
    return;
}
```

而 `PressureModel_ValidateInput` 含 `input->target_rpm >= params->min_rpm`。
一旦越界 → **整个植物状态原地保持**；由于 `motor_rpm` 的更新在 substep 内部
（在回退点之前），电机继续走，压力却冻住 —— 表现为"压力不动但泵在转"。

**为什么这是缺陷而不是保护**：设计文档
（`docs/superpowers/plans/2026-06-12-pressure-model-closed-loop.md`）明确写的是
`clamped_target = clampf(target_rpm, min_rpm, max_rpm)` —— **饱和**，不是拒绝。
真实伺服驱动也是限幅，不会"整台机器静止"。

**修复**（`src/sim/PressureModel.c`）：把越界改为**限幅**，并新增诊断位
`PressureModelOutput.command_saturated`，让上层能区分"驱动到限"与"泵/管路故障"。

**影响面**：任何"指令超出泵能力"的工况（负流量泄压打满、泵反转下限不足）都会
**静默冻结仿真**。这与一直在排查的"负流量泄压"问题直接相关。

### 11.5 实现：升压段实验限流（用户要求 #2）

**新增 API**（`include/rbf_pid.h` / `src/rbf_pid.c`）：

```c
void RBF_PID_SetBoostFlowLimit(RBF_PID_Handle *pid, float limit_lmin); /* <=0 关闭 */
void RBF_PID_SetBoostBrakeFrac(RBF_PID_Handle *pid, float brake_frac); /* 默认 0.5 */
```

**默认关闭**（`boost_flow_limit_lmin = 0`），且是**单调收紧**的附加上限
⇒ 未调用 setter 的既有用例行为逐字节不变。`RBF_PID_Reset()` 会保留该配置
（现场配置量，不是运行状态）。

**为什么不是简单硬砍（制动包络推导）**

被控对象（压力域一阶）：`dP/dt = (K·Q − P)/τ`。令
`Q_ss = P_set/K`（维持目标压力的稳态流量）、`e_b = P_set · brake_frac`、`e = P_set − P`：

```
Q_allow(e) = Q_ss + (Q_boost − Q_ss) · min(1, e/e_b)      (e > 0)
```

代入对象方程：

```
dP/dt = (e/τ) · [ 1 + (K·Q_boost − P_set)/e_b ]
```

即闭环**仍是指数逼近目标**，等效时间常数

```
τ_eff = τ / [1 + (K·Q_boost − P_set)/e_b]   ≪ τ
```

且 `e → 0` 时 `Q → Q_ss`，**等效平衡压力恰好 = P_set** ⇒ 无稳态超调、无极限环。
这是位置规划器 `sqrt(2·a·s)` 制动律在压力域的对应形式
（位置域"速度–位移"制动 ≡ 压力域"流量–压差"制动）。

**单调安全性**：`e > 0` 时返回值恒 ≥ `Q_ss`、≤ 硬限幅；`e ≤ 0` 时返回硬限幅（不收紧）。
叠加在既有 soft cap / overdrive cap 之上只会让流量更小。

### 11.6 管路 3.5 m 物理标定（用户要求 #3）

按真实几何推导，**不再手调**：

```
惯性   I = ρ·L/A                [Pa·s²/m³]
层流阻 R = 128·μ·L/(π·d⁴)        [Pa·s/m³]
```

取 ISO VG46 @40 °C（ρ = 870 kg/m³，μ = 0.041 Pa·s）、L = 3.5 m（3~4 m 中值）、
假定内径 d = 12 mm（**唯一剩余假设**，等实测确定）：

| 项 | 值 |
|---|---|
| 惯性 I | **2.69e7 Pa·s²/m³** |
| 层流阻 R | **2.82e8 Pa·s/m³** |
| 管路 LC 谐振 | 1/(2π√(I·C_ser)) = **67 Hz** |
| 四分之一波长校核 | a/(4L) = 1200/(4×3.5) = **86 Hz** ✓ 量级一致 |

内径敏感性（L = 3.5 m 固定）：d=10 mm → I=3.88e7 / 56 Hz；d=12 mm → I=2.69e7 / 67 Hz；
d=16 mm → I=1.51e7 / 90 Hz。

**为什么不再用旧的准静态值（I = 1e8，R = 2e11）**：旧值是为了让 `dt·R = 2e8 > I = 1e8`
成立（把管路变成代数环节）而凑的**数值便利**，不是物理结论。R = 2e11 意味着额定
42.5 L/min 时管压降 1417 bar —— 不可能。而且它使管路**完全不带动态**。

**数值稳定性**（模型自带的两道闸门均通过）：

| 检查 | 值 | 限 | 结论 |
|---|---|---|---|
| `stiffness_ratio = β·dt²/(I·min(V))` | 2.4e6/I = 0.089 | ≤ 0.25 | ✓ 2.8× 余量 |
| `ω·dt`（显式欧拉） | 0.42 | < 2 | ✓ 稳定 |
| 阻尼比 ζ = R/(2√(I/C)) | 0.0124 | — | 弱阻尼（真实管路本就如此） |

**⚠ 有效管长窗口**：由 `stiffness_ratio ≤ 0.25` 反解得 **L ≥ 1.25 m**。
实测 L = 1.0 m 时 `PressureModel_ValidateParams` **拒绝**该参数组，
植物永远输出保持值 —— 压力从 0 起不来（实测 Mp = −100%）。
若最终实测管长 < 1.25 m，**必须先给管路积分加子步**，不能直接跑。
该边界已固化为 `test_boost_flow_limit.c` 的断言 E。

### 11.7 关键更正：上一轮"56~67% 超调"是非物理管路的假象

同一控制器、同一真实泵权限，只改管路参数：

| 管路 | I [Pa·s²/m³] | R [Pa·s/m³] | 无限流 Mp | 无限流 tr | 无限流 ess |

| 旧（准静态） | 1.0e8 | 2.0e11 | **66.67%**（峰值 250 bar 撞溢流阀） | 107 ms | −0.44 |

> **结论修正**：第 10 节 P2 的"升压段必然超调 56~67%"**不成立**，它是仿真台保真度

> 的调试旋钮。这一点必须如实说明，不能拿旧数字去论证新机制的必要性。

| P_set [bar] | Mp [%] | tr [ms] | ts [ms] |
|---|---|---|---|
| 50 | 0.09 | 183 | 582 |
| 100 | −0.14 | 178 | 656 |
| 150 | **−0.03** | 296 | **456** ✓ |
| 200 | −0.10 | 352 | 543 |
| 250 | −0.10 | 426 | 651 |

限流把超调彻底压平（Mp −0.03%），并在 150 bar 处把 ts 拉进指标，
但 tr 付 3.5×、且 ts 在其余目标压力下仍不达标 —— **限流不是 ts 的解药**。

### 12.2 根因证据：压力轨迹（150 bar，现状代码）

```
  t[ms]    P[bar]  Q[L/min]       rpm       err
      0      0.00    31.656    1266.3    150.00   <- 超调播种：31.7 L/min
     50     39.02    16.756     670.2    110.98
    100    153.09    -2.500    -100.0     -3.09   <- 已冲过目标（Mp 2%）
    150    146.12    -0.887     -35.5      3.88
    200    135.57     0.788      31.5     14.43   <- 上限被收回 1.05*Q_ss，压力反跌
    300    130.32     0.788      31.5     19.68   <- 误差 20 bar，却只给 0.79 L/min
    450    126.48     0.788      31.5     23.52   <- 最低点，离目标 23.5 bar
   1000    137.75     0.783      31.3     12.25   <- 以 0.79 L/min 爬行
   2000    149.60     0.751      30.0      0.40   <- 2 秒才爬回
```

`t=200 ms` 起 `Q` 被钉在 **0.788 L/min = 1.05·Q_ss**（软上限），
而 `err = 14~24 bar` —— 此时超调驱动本应授权到
`(P_set/K)·(1+40·rel_err)·1.05 ≈ 4.4~5.0 L/min`（**5.6~6.4 倍**），
但闸门条件 `P_actual >= peak − 0.5` 因压力回落而**关闭**，授权被撤销。

**机理**：峰值闸门的本意是「区分升压瞬态 vs 保压纹波」，但
`rbf_pid_overdrive_cap()` 在 `rel_err → 0` 时**本就退化为软上限**
（`(1+40·0)·1.05 = 1.05`），因此该闸门对保压纹波**没有任何额外保护**；
它唯一实际作用是在**最需要驱动的超调恢复段**把驱动掐掉。

**旁证**：把阈值扫描为 −1 / 0.005 / 0.01 / 0.02，得到**完全相同**的结果
（582 / 625 / 561 / 528 ms）——恰好说明闸门在保压段恒等，只在恢复段有害。

### 12.3 新缺陷 D11【严重·潜伏】升压限流值低于维持流量 → 目标压力永不可达

`rbf_pid_boost_flow_cap()` 第 554–557 行：

```c
if (q_ss > q_boost) {
    q_ss = q_boost;   /* 限流值低于"维持流量"时，以限流为准 */
}
```

当 `Q_lim < P_set/K` 时，制动包络退化为常量 `Q_lim`，稳态压力被钉在
`K·Q_lim`，**永远达不到目标**，且无任何诊断输出。

实测（真实链，K = 200）：

| Q_lim [L/min] | ess@100 | ess@150 | ess@200 | ess@250 |
|---|---|---|---|---|
| 0.2 | −60.84 | −110.83 | −160.83 | −210.83 |
| 0.5 | −0.50 | −50.56 | −100.56 | −150.56 |
| 1.0 | −0.10 | −0.35 | −0.84 | −50.82 |
| 2.0 | −0.09 | −0.35 | −0.52 | −0.57 |

**闭式规律完全吻合 `ess = K·Q_lim − P_set`**（如 Q_lim=0.5、P_set=150 → 100−150 = −50）。

本机 K = 200 时下界仅 1.25 L/min，现场不易踩到；但 **K 是标定量**：
若换成 `Ksys = 1 bar/rpm` + 25 cc 的机型，`K = 40 bar/(L/min)`，
250 bar 的下界升到 6.25 L/min，**现场按「经验值 5 L/min」限流就会静默失效**。

**修复（已仿真验证）**：把「压低维持流量」改为「抬高限流」：

```c
if (q_ss > q_boost) {
    q_boost = clampf(0.0f, q_ss, hard_limit);   /* 保可达性；超调仍由制动包络守 */
}
```

修复后全部不可达工况消失（ess 统一收敛到 −0.10 ~ −0.58 bar，与限流值无关）。

### 12.4 测试台保真度缺陷 D3-残余：抽象 1:1 链路把 tr/ts 判成 FAIL，结论方向相反

`test_pressure_target_verification.c` 用 `FLOW_TO_RPM_GAIN = 1.0`（1 L/min ≙ 1 rpm），
即**流量权限只有 90 rpm / 450 bar**，相对 150 bar 目标仅 **3×**；
真实机是 `42.5 L/min → 1700 rpm → 8500 bar`，相对目标 **57×**。

| 链路 | 流量权限比 | Mp | tr | ts |
|---|---|---|---|---|
| 抽象 1:1（该用例） | 3× | 0.91% | **561 ms** ✗ | **606 ms** ✗ |
| **真实机（本机）** | **57×** | 3.69% | **83 ms** ✓ | 1670 ms（现状）/ 561 ms（修复后） |

⇒ 该用例的 `tr FAIL` 是**台架缩放不匹配**的产物，**不能作为调参依据**；

否则会持续把调参方向带偏（例如去追一个并不存在的 `tr` 问题）。

### 13.3 新缺陷 D12【严重】反馈噪声经增量式 PID 放大，必须依赖前置滤波

`pressure_controller.c` 在生产链路里对反馈做一阶前置滤波
（`HYD_DEFAULT_PRESSURE_FILTER_ALPHA = 0.1`）。**测试台此前没有复现它**。

原因是本机回路增益 K = 200 bar/(L/min)：维持 100 bar 只需约 0.5 L/min 流量，
而传感器噪声 σ=0.4 bar 经增量式 PID 的比例增量项 `kp·(e−e₁)` 与
`KD·(e−2e₁+e₂)`（二阶差分对白噪声放大 √6）后，变成 **σ≈0.23 L/min 的流量抖动**，
在 K=200 下等价 **±46 bar** —— 与维持流量同一量级，回路被噪声主导。

实测（真实链，100 bar 保压 24 s）：

| 前置滤波 α | ess [bar] | 判定 |
|---|---|---|
| 无滤波 | −2.374 | ✗ |
| 0.20 | −1.676 | ✗ |
| **0.10（生产配置）** | **−0.601** | ✓ |
| 0.02 | −0.289 | ✓ |

**⇒ 这不是控制器缺陷，而是测试台保真度缺口。** 已在
`test_pressure_target_verification.c` 中补上 α=0.1 前置滤波（并写明原因），
否则该用例会长期误报 ess FAIL。

前置滤波 α=0.1 的等效滞后约 10 ms，而本机上升时间只有 71~85 ms。
实测 0→150 bar（真实链）：

|---|---|---|---|---|

| 0.30 | 关 | 11.24% | 75 ms | 426 ms |

而且限流打开后超调对 α **几乎不敏感**（8/12/16 L/min 都给 Mp ≤ 0.5%），
即限流把"α 与超调的强耦合"切断了 —— 这解释了为什么现场凭经验就能用限流压住超调。

### 13.5 新缺陷 D14【严重】α 的两难：保压要小、升压要大，单值无解

| 需求 | α 要求 | 依据 |
|---|---|---|
| 保压 ess ≤ 1 bar | **α ≤ 0.1** | α=0.2 → ess −1.676 bar FAIL |
| 升压 Mp ≤ 5%（无限流） | **α ≥ 1.0** | α=0.5 → Mp 5.47% 已超标 |

**⇒ α 必须按段配置**（`pressure_controller.c` 的
`HYD_ResolveFilterAlpha()` 已支持 `segment->pressureFilterAlpha`，机制现成）：

- **升压/阶跃段**：α ≈ 1.0（或 0.3~1.0）**并且**开启升压限流
- **保压/稳态段**：α = 0.1

### 13.7 诚实结论：5 项目标仍不能同时达标

| # | 事项 | 状态 |
|---|---|---|
| 1 | 峰值闸门 → 误差幅值闸门 | ✅ 已落地，回归全绿 |
| 2 | D11 可达性下界 | ✅ 已落地，F 组断言锁死 |
| 3 | 实测压力管内径/长度 | ⏳ 现场动作，未做 |
| 4 | 测试台改真实泵参数 | ✅ 已落地（并补前置滤波，见 D12） |
| 5 | **ts 最后一公里** | ❌ **未解决**，且现在知道它与 α **耦合** |
| 6 | 现场标定升压限流值 | ⏳ 待现场，但已有仿真推荐值 12 L/min |

**为什么 ts 更难了**：先前以为 ts 只受峰值闸门影响；现在确认它是三者的耦合 —
前置滤波滞后（D13）、升压限流把 tr 拖长（13.4 中 tr 83→296 ms）、
以及窄带内的噪声整流（D12）。三个旋钮（α、Q_lim、brake_frac）只有两个自由度，
**单靠整定无法同时满足 tr ≤200 与 ts ≤500**。

**下一步需要用户决策的方向（互斥，只能选一）**：

- **方案 A：放宽 tr 到 ≤300 ms**，换取 ts 进入 500~700 ms。改动最小，只需按段配 α。
- **方案 B：把"升压上限"与"稳态上限"解耦**（升压段允许大流量快速到达、
  接近目标前切换到小流量精调），即同时放宽 tr 与 ts 的约束。

## 14. IEC → PID 数据链勘察与贯通（第 10 轮，v10）

用户指令（原话）：
> 选方案C，并且要把油泵电机的转速、转矩和反馈角度，看看能不能利用上？把数据链从

> 初始化配置，从而计算得到最大流量，把这数据链查清楚，并打通。

### 14.0 一句话结论

数据链**原本断在两处**（泵电机反馈从未被算法消费、systemGain 无 IEC 入口），
另有一处**是通的但没有闭环语义**（铭牌参数→最大流量）。本轮把三处全部接通，
并新增 `tests/test_iec_pid_datalink.c`（62 项断言）作为链路的**逐段回归护栏**。
全量 ctest **61/61** 通过。

### 14.1 勘察结果：链路逐段现状（改前）

| # | 链路区段 | 改前状态 | 证据位置 |
|---|---|---|---|
| ① | IEC `HYD_WRITEPARAMETER(PUMP_DISPLACEMENT/_VOLUMETRIC_EFF/_MAX_SPEED)` → `fb->pumpConfig` | ✅ 已通 | `motion_control.c:4212-4214` |
| ② | `fb->pumpConfig` → `flowToPumpSpeedGain` = `1000/(D·η)`、`pumpSpeedLimit` = `maxSpeedRpm` | ✅ 已通（每周期现算） | `motion_control.c:2301-2307`、`2410-2416` 等 8 处 |
| ③ | `pressureInput.*` → `HYD_EnsureRbfPidInitialized` → `fMaxFlow = limit/gain` | ✅ 已通 | `pressure_controller.c:288-328` |
| ④ | **`fMaxFlow` 对外可读回 / 单一真源** | ❌ **无**（只在 execute 内部隐式存在；`HYD_PARAM_MAX_FLOW` 是死字段，与推导值双来源） | — |
| ⑤ | **`systemGain` 的 IEC 初始化入口** | ❌ **无**（只有段级 `HYD_MotionSegment.systemGain`，无参数 ID） | `common_types.h:401` |

即：**用户在指令里点名的三件事，恰好就是断掉的 ④⑤⑥ 三处**；①②③ 本来就是通的。
这也解释了为什么此前"配了泵参数但感觉限幅没生效"——链路本身通，
但算出来的最大流量**看不到、也没跟手填值建立优先级关系**，所以无法自证。

### 14.2 关键换算（用户机实际泵，25 cc/rev @ 1700 rpm）

```
第 1 步  IEC 写铭牌：  displacementMlRev = 25, volumetricEfficiency = 0.95, maxSpeedRpm = 1700
第 2 步  派生转速增益： gain = 1000 / (25 × 0.95)            = 42.1053 rpm/(L/min)
第 3 步  派生最大流量： Q_max = 1700 / 42.1053               = 40.375 L/min
        等价写法：      Q_max = 1700 × 25 × 0.95 / 1000      = 40.375 L/min   ← 铭牌直算式
第 4 步  系统增益（若由 IEC 下发）： K = Ksys / (D/1000) = 5.0 / 0.025 = 200 bar/(L/min)
```

**注意 40.375 ≠ 42.5**：42.5 = 25×1700/1000 是**理论几何流量**（η=1）；
考虑容积效率 0.95 后是 40.375 L/min。二者混用是常见错误源，
本轮把 `HYD_PumpConfig_GetMaxFlowLmin()` 定为唯一实现，杜绝两处各算一遍。

### 14.3 本轮落地（v10）

#### (1) 铭牌 → 最大流量：新增显式真源与可读回闭环

- `common_types.h`：新增 `HYD_PumpConfig_GetMaxFlowLmin(cfg)`（= `maxSpeedRpm / gain`）。
- `motion_control.h/.c`：新增公共 API `HYD_MotionControlFB_ResolveMaxFlowLmin(fb)`，优先级固定为
  **① pumpConfig 铭牌 → ② 旧版 gain/limit → ③ `HYD_PARAM_MAX_FLOW` 手填 → ④ 0**。
  铭牌放最高优先级：它是电机的物理事实，而 gain/limit 是派生量，手填容易与铭牌不一致。
- 新增**只读**参数 `HYD_PARAM_MAX_FLOW_DERIVED`：写 `PUMP_*` 参数后立即回填，
  于是 IEC 侧可以「写铭牌 → 读回算出来的最大流量」，链路自证闭环。
  对它写入会被拒绝（返回 ERROR），避免"配置真源被悄悄改掉"。

#### (2) 系统增益 K：新增 IEC 初始化入口

- 新增 `HYD_PARAM_PRESSURE_SYSTEM_GAIN`（追加在枚举末尾，**既有编号全部不变**，
  不破坏已固化的 IEC 参数编号）。
- 解析优先级（`HYD_ResolvePressureControllerConfig`）：
  **段级 `segment->systemGain` > IEC 下发的 `input->systemGain`**。
  段级用于"同一台机不同动作段刚性不同"（射胶段刚性 > 合模段），
  IEC 级作为全机默认值 —— 这正对应指令里的"由 IEC 进行初始化配置"。

#### (3) 泵电机反馈（rpm / 转矩 / 角度）→ 算法

换算：`actual_flow = rpm / flowToPumpSpeedGain`（`common_types.h` 新增
`HYD_PumpFeedback_GetActualFlowLmin`，**保留符号**：rpm<0 即负流量泄压）。

| 反馈量 | 本轮用途 | 设计取舍 |
|---|---|---|
| **rpm 转速** | ① 观测：`actualFlow`、`flowTrackingError`；② **抗积分饱和**：实测转速贴限 → 把 PID 软上限收缩到实测可达流量（back-calculation anti-windup） | 只收紧**上限**，不碰下限 → 负流量泄压路径零影响 |
| **转矩 torquePermille** | 过载判定：超 IEC 配置阈值 → `pumpTorqueOverload` 标志（供上层限流/报警） | 阈值 0 = 关闭，**默认关闭** |
| **角度 angleDeg** | 仅对外观测（本层不参与控制决策） | 伺服泵相位对压力闭环价值低，避免引入不可验证的复杂度 |

抗饱和的关键判断（两处"防误伤"）：
1. **反转不算饱和**：泵反转满速是**泄压能力充足**，不是"加不了流量"。
   `pumpSpeedSaturated` 只对**正向贴限**置位，且反转时 cap 恒不武装。
2. **无有效性位即不介入**：`validFlags` 无 `VALID_RPM` 位时，cap 关闭 + 观测置 0，
   逐位退回 v9 行为 —— 现场没接反馈硬件也能安全运行。

#### (4) 方案 C：合格口径收敛为 3 项

`tests/test_pressure_target_verification.c`：
- **升压段只看 Mp**（合格线 ≤5%）；**保压段只看 ess / σ**（各 ≤1 bar / 1 bar RMS）。
- **tr / ts 降级为诊断量**（输出用 △ 标注，不判不合格）：它们受前置滤波滞后支配
  （α=0.1 的等效滞后约 10 ms，占本机上升时间 71~85 ms 的 12~14%），
  而"降 α 保 tr"与"升 α 保 ess"互相冲突 → 单靠整定无解（§13.5 的 D14 两难）。
- 仍保留**回归护栏**断言（tr ≤400 ms、ts ≤1000 ms，远宽于参考目标 200/500 ms），
  只挡性能大幅退化，不作为合格判据。

#### (5) 顺带修掉一个真实隐患：输入结构未清零

`HYD_ProduceControlOutputs` 里 `pressureInput` / `pumpInput` 是栈局部变量且**从未 memset**
（输出结构都 memset 了，输入没有）。改前之所以没出事，是因为**每个字段在每个分支都被
显式赋值**；但本轮新增 7 个字段后，只要漏赋一个就变成"读栈垃圾"的静默缺陷 ——
`test_pressure_controller` 当场失败即为实证（症状是策略切换后输出流量跳变）。

已加 `memset` 并把测试侧的声明统一改为 `= {0}`（37 处，跨 7 个测试文件）：
那些测试此前依赖未定义行为，属**真实的测试卫生缺陷**，只是被"字段恰好被赋值"掩盖了。

## 15. 上机量产就绪度评估（第 11 轮，2026-09-17）

### 15.0 一句话结论

**不具备。** 差的不是算法，而是**三条"线还没接"**：

1. 【阻断】升压限流在 `src/` 里**没有任何调用者** —— PLC 侧无法开启它，而它是 Mp 达标的**必要条件**；
2. 【阻断】库默认 `pressureFilterAlpha = 1.0`（=不滤波），实测保压 ess **3.763 bar（超 3.8 倍）FAIL**；
3. 【阻断】**零现场验证** —— 全部结论来自仿真。

第 2 条有 IEC 通路（改配置即可），**第 1 条连通路都没有**。

### 15.1 决定性证据：三个旋钮的实测矩阵

用同一套真实机链路（25cc/rev @ 1700rpm、K=200、管路 3.5m、含噪声，
测试台 `tests/test_pressure_target_verification.c`，仅改配置项）：

| α（前置滤波） | 升压限流 | 升压 Mp | 保压 ess | 保压 σ | 判定 |
|---|---|---|---|---|---|
| **1.0（库默认）** | **0（库默认）** | −0.03%（无超调） | **+3.763 ✗** | 0.482 ✓ | **2/3 ✗** |
| 0.1（生产值） | **0（库默认）** | **32.03% ✗** | 0.654 ✓ | 0.410 ✓ | **2/3 ✗** |
| 0.1（生产值） | 12（生产值） | 0.46% ✓ | 0.654 ✓ | 0.410 ✓ | **3/3 ✓** |

**读数**：
- **两个旋钮必须同时设对**，各错一个都是 FAIL —— 不存在"默认可用"的侥幸。
- 两个旋钮的**默认值方向都是错的**：α 默认 1.0（要 0.1）、限流默认 0（要 12）。
- 最刺眼的是第 2 行：即便 α 调对了，只要限流是默认值，Mp 就 **32.03%（超标 6.4 倍）**。

### 15.2 阻断项（上机前必须解决）

#### B1【阻断】升压限流没有任何 PLC/库侧启用通路

```
$ grep -rn "SetBoostFlowLimit" src/ include/ | grep -v rbf_pid.c
include/rbf_pid.h:328:  void RBF_PID_SetBoostFlowLimit(RBF_PID_Handle *pid, float limit_lmin);
src/sim/PressureModel.c:443:  /* 注释，非调用 */
```

- `include/common_types.h` 中**没有任何 `HYD_PARAM_*_BOOST_*`**；
- `HYD_MotionSegment` 中**没有 boost 字段**；
- `HYD_ApplyRbfPidConfig()` 中**没有调用** `RBF_PID_SetBoostFlowLimit`。

⇒ 该配置**只能由 C 代码直接调用 API 设置**。PLC 侧无路可走。
⇒ 结合 15.1 第 2 行：**现场按 PLC 正常配参，Mp 必然是 32%**。

这条是"现场"升压段必须限流"这一经验在库里落不下去"的根因 ——
参数早就实现了（v8），但从头到尾**没接过线**，因而所有既有回归都测不到它（默认关闭，
测试台是直接调 API 才打开的）。

#### B2【阻断】默认滤波系数导致保压不达标

- `src/motion_control.c:3613`：`fb->_params.pressureFilterAlpha = 1.0f;`（=不滤波）
- `src/motion_interface.c:311/365`：`seg.pressureFilterAlpha = fb->_params.pressureFilterAlpha;`
  → 经 IEC 建立的每个段都继承 **α=1.0**
- 实测（15.1 第 1 行）：ess = **+3.763 bar**，合格线 1 bar → **FAIL**

通路是有的（`HYD_PARAM_PRESSURE_FILTER_ALPHA` 可写），所以这条属于
**"默认值不安全 + 缺少配置约束"**：现场若漏配，现象是"保压压力偏高约 3.8 bar"，

### 15.4 本轮附带修掉的一个测试口径缺陷

评估过程中发现**判定 Mp 的逻辑本身是错的**：

```c
pass_s1_mp = (mp_pct >= 0.0f && mp_pct <= TARGET_Mp_PCT);   /* 旧 */
```

响应若恰好未超过目标，峰值略低于 150 bar（实测 α=1.0 时峰值 149.95），
`mp_pct = −0.03%` —— 那是**完全无超调**，却被 `>= 0.0f` 判成 FAIL。
（`>= 0` 本意是排除 `mp_pct = −1.0` 的哨兵值，但"是否真到目标"已由 `s1.reached` 单独把关。）

已改为物理等价且口径正确的判据：

```c
pass_s1_mp = s1.reached && (s1.p_max <= 150.0f * (1.0f + TARGET_Mp_PCT / 100.0f));
```

修正后 α=1.0 由"1/3"变"2/3"，α=0.1 仍为 3/3（不影响生产判定）。

## 17. 量产就绪度复评（第 13 轮，2026-09-17）

### 17.0 一句话结论

**仍不具备上机量产实用性，且本轮发现一个比 §15 更关键的阻断项。**

§16 的结论"默认配置已安全"**只对 RBF 路径成立**。本轮把评估口径改为**真实出厂默认**后实测：

### 17.1 决定性证据：控制器策略 × 升压限流 实测矩阵（8 组）

同一入口 `HYD_PressureController_Execute`、同一真实机链路
（25cc/rev @ 1700rpm、K=200 bar/(L/min)、管路 3.5m、α=0.1），仅改策略/增益/限流：

| 组 | 配置 | 升压 Mp | 保压 ess | 保压 σ | 达标 |
|---|---|---|---|---|---|
| **A** | **出厂默认**（PI kp=1.5, ki=0，无限流） | **+66.67% ✗** | **−10.355 ✗** | **13.035 ✗** | **0/3** |
| B | PI kp=1.5, ki=0 + 限流 12 | +66.67% ✗ | −10.355 ✗ | 13.035 ✗ | 0/3 |
| C | RBF_PID（无限流） | +35.50% ✗ | +0.556 ✓ | 0.439 ✓ | 2/3 |
| **D** | **RBF_PID + 限流 12（生产推荐）** | **−0.04% ✓** | **+0.587 ✓** | **0.426 ✓** | **3/3** |
| E | PI kp=0.025, ki=0（低增益纯 P） | −1.00% ✗ | +16.670 ✗ | 0.435 ✓ | 1/3 |
| F | PI kp=0.025, ki=0 + 限流 12 | −1.00% ✗ | +16.670 ✗ | 0.435 ✓ | 1/3 |
| G | PI kp=0.3, **ki=0.05**（补积分） | +66.67% ✗ | +0.116 ✓ | 0.436 ✓ | 2/3 |
| H | PI kp=0.3, ki=0.05 + 限流 12 | +66.67% ✗ | +0.116 ✓ | 0.436 ✓ | 2/3 |

### 17.2 三条**独立**的读数（每一档都指向同一个结论）

**读数 1 —— 出厂默认实测 0/3，比 §15 记载的"2/3"更差。**
§15.1 的矩阵是在 **RBF_PID 策略**下得到的（`test_pressure_target_verification.c`
第 167 行显式写死 `pressureController=HYD_PRESSURE_CONTROLLER_RBF_PID`）。
而 `src/motion_control.c:3631` 的**真实出厂默认是 `PI`**。把口径换成真实默认后：
- Mp **+66.67%**（直接冲到 250 bar 压力上限被削顶）
- ess **−10.355 bar**（稳态压力比目标**高 10.4 bar**）
- σ_ss **13.035 bar RMS**（剧烈振荡）、ts **4995 ms**（5s 内从未稳定）
⇒ 出厂默认在真实机上是一个**振荡、削顶、稳态大幅偏高**的回路。

**读数 2 —— B ≡ A 逐位相同，证明 PI 路径完全不吃升压限流。**
A 与 B 只差"限流 12 是否打开"，四种指标**完全一致**。原因见 §17.3：
v11 的 `RBF_PID_SetBoostFlowLimit()` 接线位于 `HYD_ApplyRbfPidConfig()` 内，
而该方法**只在 RBF 分支（`pressure_controller.c:755`）被调用**。
⇒ **v11 修复的 B1，对默认策略（PI）无效。** §16.5 把它记为"✅ 就绪"是**口径过宽**。

**读数 3 —— PI 不是"调不好"，而是"结构性达不到 Mp"。**
- E/F：把 kp 降到 0.025（环路增益 5）→ 稳态误差 **+16.67 bar**、tr=−1（**从未达 90%**）。
  根因：**PI 策略的 ki 兜底值是 0**（`HYD_ResolveGain(segment->pressureKi, 0.0)`），
  **PI 在默认/未配 ki 时退化为纯 P**，而纯 P 在 K=200 下无法同时兼顾 ess 与抗噪。
- G/H：补上 ki=0.05 后 ess/σ 达标，但 **Mp 仍 +66.67% FAIL** —— 因为
  **PI 路径没有任何升压段限流手段**（唯一上限是 `outputMax` 全局钳位，
  而全局钳位同时会限制保压能力）。
⇒ **PI 策略在本机单位链下无法同时满足 3 项**，这不是调参问题，是策略能力问题。

### 17.3 根因：默认策略与真实单位链不匹配（两个叠加的历史遗留）

1. **默认策略是 PI**（`motion_control.c:3631`），而 RBF 整定工作全部不在默认路径上。
2. **PI 的默认增益 kp=1.5 是"抽象链路时代"的值**（`HYD_LEGACY_PRESSURE_FLOW_KP`）。
   抽象链路 K=5 → 环路增益 7.5（尚可）；真实链路 **K=200 → 环路增益 300**，
   把 σ=0.4 bar 的传感器噪声放大成 **13 bar RMS** 的持续振荡。
   ⇒ 单位链从抽象改到真实（v9）时，**PI 默认增益没有同步重标定**。

叠加结果：现场若原样使用出厂默认，压力回路是**不可用**的。

## 18. §17 更正 + v12 落地（第 13 轮修正，2026-09-17）

### 18.0 一句话结论

**§17 的 A 组数据是错的**（探针未复现真实默认增益）。更正后：出厂默认实体是
**PI kp=0.5, ki=0.1**（非 kp=1.5, ki=0）；真实阻塞点是 **`systemGain`（K）= 0** ——
K 是 RBF-PID 的**核心过程增益**，K=0 会让整定链路失效。v12 已把
**默认策略改为 RBF_PID + 从泵铭牌推导 K 与升压限流**，端到端验收
**出厂默认（仅配泵铭牌）3/3 达标**。

### 18.1 §17 的三处口径错误（更正）

| # | §17 的错误 | 事实（源码） |
|---|---|---|
| ① | PI 默认增益 "kp=1.5, ki=0" | **kp=0.5, ki=0.1**（`motion_control.c:3609/3612`）。§17 探针未设 `segment.pressureKp/Ki` → 走了库内 fallback `HYD_LEGACY_PRESSURE_FLOW_KP=1.5`、`ki=0` |
| ② | 流量-转速增益口径 | 真实 **42.105** = 1000/(25×0.95)；§17 探针用 40（η=1 理论值） |
| ③ | 输出上限口径 | 生产链路压力手柄 100% → maxFlow **20 L/min**（`HYD_PRESSURE_HANDLE_BASE_MAX_FLOW=20`）；§17 探针用 42.5（无手柄上限），宽松一倍 |

⇒ §17 的"出厂默认 0/3"是**基于错误增益**得到的。更正后实测：
**PI kp=0.5/ki=0.1 在生产口径下为 0/3，但失效机理与 §17 描述不同**（见 18.3）。

### 18.2 更正后的实测矩阵（同一入口 Execute，真实泵 gain=42.105，输出上限 20）

### 18.3 真正的根因：`systemGain`（K）而非"策略型"

`K` 不是可选的"增益补偿"，而是 RBF-PID 的**核心过程增益**，四处依赖它
（`src/rbf_pid.c`）：

| 用途 | 位置 | K=0 的后果 |
|---|---|---|
| Jacobian 限幅中心 `[0.2K, 5K]` | `rbf_pid.c:364-366` | 辨识不受约束，收敛慢/方向错 |
| 稳态前馈 `u₀ = P_set/K` | `rbf_pid.c:905-919` | 无前馈，靠积分慢爬 |
| 过驱动软上限 `P_set·ratio/K` | `rbf_pid.c:455/508` | 软上限失效 |
| 可达性下界 `q_ss = P_set·ratio/K` | `rbf_pid.c:575` | D11 保护失效 |

实测：C（K=0）→ 0/3；D（K=200）→ 3/3。**K 偏差 2 倍即掉到 2/3**
（K=100 → σ FAIL；K=400 → ess FAIL）。

K 有物理来源：`Ksys = P_chamber/n` 是"过程层已知的机器常数"
（`PressureModel.c:469`），`K = Ksys/(D/1000)`。

### 18.4 v12 落地改动（让出厂默认即达标）

| 文件 | 改动 |
|---|---|
| `src/motion_control.c` | ① 默认策略 `PI` → **`RBF_PID`**；② 新增 `HYD_DEFAULT_PRESSURE_KSYS_BAR_PER_RPM=5.0`；③ `systemGain` 未显式配置时按 `K = Ksys/(D/1000)` **从泵铭牌推导**；④ `boostFlowLimit` 未显式配置时按 `q_boost = clamp(0.30·Q_max, 3·P_ceiling/K, Q_max)` 推导（下界是 D11 可达性要求的 3 倍裕度） |

### 18.7 口径一致性审计（v12 复查，2026-09-17）

**为什么做这一节。** 用户在第 13 轮明确指出：§17 曾把 PI 出厂默认 `kp/ki` 读成
`1.5/0`（实际 `0.5/0.1`），"结论与结论不相符"。这暴露的不是一个孤立的读数错误，
而是**一类系统性风险**：v12 改变了 `0` 的语义（"关闭" → "按铭牌推导"），
但凡 v12 前写下的注释/头文件说明没有同步，后来者就会读到**与代码行为相反的口径**。
因此本轮专门做了一次"语义变更 × 全部落点"的一致性审计。

#### 18.7.1 审计发现的 5 处矛盾（均为"注释/接口说明 vs 代码行为"）

| # | 位置 | 旧口径（v11 前语义） | 与 v12 代码实际的矛盾 |
|---|---|---|---|
| 1 | `motion_control.c` Init 默认值注释块 | `systemGain = 0 → 不启用增益补偿` | v12 后 0 = **按泵铭牌推导 K**，非不启用 |
| 2 | 同上 | `boostFlowLimit = 0 → 关闭升压限流` | v12 后 0 = **按 `Q_max` 推导**，非关闭 |
| 3 | 同上 | `…必须由 IEC 显式下发` | 已不再"必须"，铭牌推导可兜底 |
| 4 | `common_types.h` `HYD_MotionFBParams` | `systemGain`="段级缺省时的回退值"；`boostFlowLimit`="0 = 关闭" | 同上两处 |
| 5 | `pressure_controller.h` `HYD_PressureControllerInput` | `boostFlowLimitLmin <= 0 表示关闭限流` | v12 后 `<=0` 是"上游未提供"，推导在上游完成 |

另有 **1 处措辞性但影响理解**的表述：`pressure_controller.h` 原称 `systemGain` 为
"**RBF-PID 增益补偿用**"。这与 §18.3 的更正结论（K 是**核心过程增益**，四处依赖，
不是可选补偿）冲突，是 §17 同一误解的残留，一并改为"核心过程增益"。

#### 18.7.3 顺带复核的一个"疑似真矛盾"（结论：不是矛盾）

审计时怀疑：`_params.maxFlow = 90.0`、`flowToPumpSpeedGain = 20`、`pumpSpeedLimit = 1800`
这组**遗留旧值**（与真实泵 `42.105 / 1700` 不符）会不会污染 v12 的升压限流推导，
使 `q_boost = 0.30 × 90 = 27` 而非实测的 `12.11`。

复核 `HYD_MotionControlFB_ResolveMaxFlowLmin`（`motion_control.c:182`）后确认**不会**：

```
优先级 1  铭牌派生  HYD_PumpConfig_GetMaxFlowLmin(pumpConfig)   ← 25cc/1700/0.95 → 40.375
优先级 2  遗留回退  PUMP_SPEED_LIMIT / FLOW_TO_PUMP_SPEED_GAIN   ← 1800/20 = 90
优先级 3  手填回退  _params.maxFlow                              ← 90
```

铭牌有效时走优先级 1（`0.30 × 40.375 = 12.11`，与实测吻合）；
铭牌**无效**时走 2/3（`90`），但此时 **K 同样推导不出**（K 推导与限流推导
共用 `pumpConfig` 有效这一前置条件），限流推导因 `systemGain > 0` 不成立而整段跳过。
**两个推导被同一前置条件锁在一起，因此不存在"用错 Q_max 算出错误限流"的路径。**
结论：遗留旧值只在"连铭牌都没配"的降级场景生效，且该场景下 K=0 → 链路本就不可用，
属已登记遗留项（§18.6），无需在 v12 内额外处理。
